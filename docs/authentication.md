# Phase 2: identity and access

## How a sign-in works

1. The browser posts JSON email/password to `POST /auth/login`.
2. The API normalizes the email, finds the database user, checks the Argon2id hash,
   and rejects inactive accounts. Wrong password and unknown email return the same 401.
3. The API signs a short-lived JWT. Its `sub` claim is the user's database ID;
   `exp`, `iat`, `iss`, and `aud` limit its lifetime and intended use.
4. The browser saves only the access token in localStorage, then fetches `GET /auth/me`
   using `Authorization: Bearer <token>`.
5. The backend validates the signature using the configured algorithm, expiry,
   issuer, and audience, then retrieves the user from PostgreSQL. Profiles are
   serialized through explicit Pydantic response schemas; hashes never leave the API.

`get_current_user` resolves identity. `get_current_active_user` additionally rejects
disabled accounts. Future protected endpoints should depend on the active-user
dependency or `require_roles(Role.MANAGER, Role.ADMIN)`. Admin is only allowed when
explicitly listed; there is no implicit bypass. Roles come from PostgreSQL, not
browser input or stale token claims. Request and approval endpoints now use the
active-user dependency and service-level ownership/assignment checks. The generic
role helper also remains covered through a test-only route.

## Employee and manager relationship

```text
users: Jamie Employee (EMPLOYEE)
    manager_id ────────────────► users: Morgan Manager (MANAGER)
                                      id
```

Both are rows in `users`; one manager can have many direct reports. `manager_id`
is nullable, indexed, and a foreign key with `ON DELETE SET NULL`. A check prevents
self-management. The seed verifies the intended roles and assignment. A future user
management service must validate manager role and prevent reporting cycles; the
foreign key guarantees existence, not organizational policy. No user-edit API is exposed.

Emails are normalized and uniquely indexed. Required columns are non-null, roles
use a PostgreSQL enum, and timestamps are timezone-aware. `updated_at` changes on
SQLAlchemy-managed updates; direct SQL writers must update it explicitly.

## Migrations and seeds

Alembic revision `0001` creates the role enum and users table. Migrations are applied
explicitly, never through `create_all` or on every API startup. Autogenerated future
migrations must be reviewed. The tests create isolated `test_<uuid>` PostgreSQL schemas,
run migrations, and roll back test data; they never clear public development tables.

The seed is an explicit demo-only operation. Running it again creates missing demo
accounts but preserves existing passwords and active flags. Conflicting roles or
manager assignments stop the transaction instead of overwriting them. It is intended
for serial developer use, not simultaneous distributed seed jobs.

## Token storage and limitations

localStorage provides reload persistence and keeps the demo easy to understand,
but any injected script can read the token. Do not insert untrusted HTML or place
sensitive data in JWT claims. JWTs are signed, not encrypted. For a sensitive system,
consider HttpOnly/Secure cookies with CSRF protection, a stricter CSP, and a reviewed
session lifecycle. Use HTTPS before publishing.

Logout removes the browser token; it does **not** revoke copies of an issued token.
Tokens expire after 30 minutes by default. There are no refresh tokens, revocation
list, password reset, registration, MFA, or login throttling in this phase. Add rate
limiting and review dependencies before the public deployment phase.

Reload restores identity through `/auth/me`. A timer clears an expired session;
window focus revalidates identity; logout synchronizes across tabs. Invalid tokens
or inactive users clear the session. Network/5xx errors display a retry screen and
retain the token instead of treating connectivity as bad credentials. The frontend
expiry decode is only for UI behavior; backend JWT verification is authoritative.

JWT_SECRET is generated locally and excluded from Git. Startup rejects short or
placeholder values. Only HS256 is supported, deliberately allowlisted in settings.
Changing the secret invalidates existing tokens. Public demo passwords are separate
from the signing secret and must never protect real company data.

Implementation references: [FastAPI JWT and password hashing](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)
and [Alembic migrations](https://alembic.sqlalchemy.org/en/latest/tutorial.html).
